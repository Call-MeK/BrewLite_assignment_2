1. Tổng quan

1.1 Mục tiêu của báo cáo
Assignment 1 đã chốt use case, user story và kiến trúc. Báo cáo này trả lời ba câu hỏi còn lại:
(i) sản phẩm có chạy thật trên môi trường production hay không; (ii) các yêu cầu chức năng
và phi chức năng đã được đáp ứng tới đâu, kèm bằng chứng; (iii) hiệu năng và chất lượng mã
nguồn có đạt ngưỡng đã cam kết hay không. Mọi số liệu trong báo cáo đều được đo trên hệ
thống đang chạy, không phải số liệu giả định.

1.3 Tài khoản dùng để kiểm thử
Hai tài khoản được tạo bởi script seed, dùng cho việc đánh giá và trình diễn: khách hàng
demo@brewlite.test / Demo@12345 và quản trị viên admin@brewlite.test / Admin@12345.
Đây là tài khoản mẫu trên môi trường Sandbox, không phải thông tin đăng nhập của người
dùng thật.

1.4 Cách tái lập
 1. Cài phụ thuộc: npm install trong apps/api và apps/web.
 2. Khởi động cơ sở dữ liệu cục bộ bằng Docker Compose, sau đó chạy npx prisma migrate
    deploy.
 3. Nạp dữ liệu mẫu bằng npm run prisma:seed (lưu ý: script này xoá toàn bộ dữ liệu cũ
    trước khi nạp lại).
 4. Chạy API bằng npm run start:dev và web bằng npm run dev; web đọc địa chỉ API từ
    biến NEXT_PUBLIC_API_URL.

4. Kiến trúc triển khai

Hệ thống gồm ba dịch vụ độc lập. Ứng dụng web được Vercel build và phân phối qua CDN;
API NestJS đóng gói trong Docker và chạy trên Render; cơ sở dữ liệu PostgreSQL đặt trên
Neon và chỉ nhận kết nối có SSL từ API. ZaloPay Sandbox gọi ngược về API qua callback
HTTPS. Mỗi lần main thay đổi, Vercel và Render tự động build lại từ mã nguồn; GitHub
Actions chạy kiểm thử và build trước đó như một cổng chất lượng.

                               Bảng 4: Chín module nghiệp vụ của API

Module               Trách nhiệm

auth                 Đăng ký, đăng nhập, cấp và kiểm tra JWT, chiến lược xác thực.
users                Hồ sơ người dùng, vai trò, danh sách khách hàng cho quản trị.
products             Thực đơn, danh mục, giá theo size, tìm kiếm và lọc.

orders               Tạo đơn, máy trạng thái, huỷ đơn, lịch sử trạng thái.

ingredients          Nguyên liệu, tồn kho, cảnh báo dưới định mức.

7. Đo hiệu năng

7.1 Phương pháp
Ba endpoint đọc dữ liệu mẫu được gọi 5 lần liên tiếp, cách nhau 300 ms, từ một máy khách
tại Việt Nam tới API trên Render (Singapore) qua HTTPS. Thời gian đo là thời gian phản
hồi đầy đủ của yêu cầu HTTP, bao gồm cả độ trễ mạng. Trước khi đo, API đã được đánh
thức để loại bỏ ảnh hưởng của cơ chế ngủ đông.

                    Bảng 8: Kết quả đo thời gian phản hồi (đơn vị: mili giây)

 Endpoint            L1    L2    L3     L4         L5   Nhỏ nhất    Trung vị     Lớn nhất    Kết luận

 /health             96     99   96     133        95          95           96         133      Đạt
 /products          116    185   165    182       194         116          182         194      Đạt
 /products/:id      104     89   81     80         81          80           81         104      Đạt


Cả ba endpoint đều đạt ngưỡng NFR-01 (dưới 500 ms) với biên an toàn lớn: trường hợp xấu
nhất là 194 ms, chưa bằng 40% ngưỡng. Endpoint danh sách có thời gian cao hơn vì trả về 8
sản phẩm kèm bảng giá theo size và thông tin danh mục.

7.2 Khởi động nguội
Lần gọi đầu tiên sau một khoảng thời gian không có lưu lượng mất 52.483 ms (khoảng 52
giây) do Render ở gói miễn phí tạm dừng dịch vụ khi rảnh. Đây là giới hạn của hạ tầng,
không phải của mã ứng dụng: sau khi dịch vụ thức, mọi phản hồi đều dưới 200 ms. Ba hướng
xử lý đã được ghi nhận: nâng gói Render để tắt chế độ ngủ, dùng bộ hẹn giờ gọi /health định
kỳ, hoặc chuyển sang nền tảng không tạm dừng dịch vụ.
